# Requirements — 自社アパレル EC サイト（ローカルモックアップ）

> Stage: requirements-analysis（Inception 2.3）· Scope: workshop · Depth: Minimal · Test Strategy: Minimal
> 入力: 元の依頼「ユニクロのような自社のECサイトを構築したいです」、`requirements-analysis-questions.md`（Q1: A,B,C,D / Q2: A / Q3: A / Q4: A）、`team-practices.md`
> `intent-statement` と `scope-document` は、workshop スコープでアイデア出しフェーズ（Intent Capture・Scope Definition）を飛ばしたため存在しない。目的と範囲は上記の依頼と回答から導いた。

## Intent Analysis

- **最終的な目標**: ユニクロのような、自社ブランドの衣料品をオンラインで販売する自社 EC サイトを持つ。
- **今回のゴール**: ワークショップの残り時間（約 1 時間）で、「商品を探す → 選ぶ → カートに入れる → 注文する」までの一連の流れを**ローカルで操作できる画面モックアップ**を作り、画面の流れと購入体験を確認する。
- **成功の判定**: `npm install` と `npm run dev` で起動し、ブラウザで商品一覧から注文完了まで操作でき、その間ブラウザのコンソールに処理されていないエラーが出ない。あわせて `npm run build`、`npm run lint`、`npm test` がすべて成功する。
- **分類**: 新規開発（グリーンフィールド）、フロントエンドのみ、複雑さは Standard（今回作る範囲は Minimal）。

## Functional Requirements

### FR-0 共通（ヘッダーと画面構成）

- **FR-0.1** すべての画面に共通ヘッダーを表示する。ヘッダーには、ブランド名（押すと商品一覧へ戻る）と、カートへのリンク（カート内の数量の合計を表示）を載せる。
- **FR-0.2** 画面とパスは次のとおりとし、React Router で切り替える。
  - `/` 商品一覧
  - `/products/:id` 商品詳細
  - `/cart` カート
  - `/checkout` 注文手続き（「配送先の入力」と「注文内容の確認」の 2 段階を同じ画面の中で切り替える）
  - `/complete` 注文完了
- **FR-0.3** 商品画像として、フリー素材サイト Unsplash の写真を商品ごとに 1 枚（計 12 枚程度）用意する。
  - 使うのは Unsplash License の無料写真だけとし、有料の Unsplash+ の写真は使わない。
  - ブランドのロゴや名前が写っている写真は使わない。
  - 写真はコード生成のときに一度だけダウンロードしてアプリに同梱し、実行時はネットワークに接続しない。
  - 撮影者名と写真ページの URL を、出典一覧（`CREDITS.md`）に記録する。
  - ダミー商品の 1 色目は写真の服の色に合わせる。
  - 写真をダウンロードできなかった商品は、商品名とカラーを書いた色付きの枠で代わりに表示する。
  - 判定: 一覧に商品ごとの写真が表示され、ネットワークを切っても表示される。`CREDITS.md` に全写真の出典がある。

### FR-1 商品一覧

- **FR-1.1** 商品をグリッドで表示する。各商品には商品写真（FR-0.3）、商品名、税込価格（円）を出す。
  - 判定: 一覧を開くと、ダミーデータの全商品がカードで表示される。
- **FR-1.2** カテゴリ（メンズ／ウィメンズ／キッズ）で絞り込める。「すべて」で解除できる。
  - 判定: 「ウィメンズ」を選ぶと、ウィメンズの商品だけが表示される。「すべて」に戻すと全件が表示される。
- **FR-1.3** 商品カードを押すと、その商品の詳細画面に移動する。

### FR-2 商品詳細

- **FR-2.1** 商品写真（FR-0.3、大きめに表示）、商品名、税込価格、説明文、カラーの選択肢、サイズの選択肢（例: S / M / L / XL）を表示する。
- **FR-2.2** カラーとサイズの両方を選ぶまで「カートに入れる」ボタンを押せない。
  - 判定: どちらかが未選択の間はボタンが無効で、両方選ぶと有効になる。
- **FR-2.3** 「カートに入れる」を 1 回押すと 1 個カートに入り、ヘッダーのカート件数（数量の合計）が 1 増える。上限に達している場合は FR-3.4 に従う。
- **FR-2.5** カラーの選択肢は色見本（丸いチップ）とカラー名で表示し、選んだものを強調する。写真は商品ごとに 1 枚で、カラーを変えても写真は変わらない。
- **FR-2.4** 存在しない商品の URL を開いたときは「商品が見つかりません」と表示し、一覧へのリンクを出す。

### FR-3 カート

- **FR-3.1** カートの各行に、商品名、カラー、サイズ、単価、数量、小計を表示する。
- **FR-3.2** 数量を 1〜10 の範囲で変更できる。行を削除できる。
  - 判定: 数量を 2 にすると小計が単価の 2 倍になる。削除するとその行が消える。
- **FR-3.3** 合計金額（税込）を表示する。
- **FR-3.4** 同じ商品・カラー・サイズを再度カートに入れると、新しい行を作らず数量を加算する。1 行の上限は 10 個で、すでに 10 個入っているときは追加せず「同じ商品は 10 点までです」と表示する（件数は増えない）。
- **FR-3.5** カートの中身は、ブラウザを再読み込みしても残る（localStorage に保存）。
- **FR-3.6** カートが空のときは「カートは空です」と表示し、注文手続きへ進むボタンを出さない。
- **FR-3.7** localStorage のカートの値が壊れている、または読み込めないときは、空のカートとして扱い、画面はそのまま表示する。
  - 判定: localStorage に不正な文字列を入れて再読み込みしても画面が表示され、カートは空になる。

### FR-4 注文手続き〜注文完了

- **FR-4.1** 配送先の入力フォームを表示する（氏名、郵便番号、住所、電話番号、メールアドレス。すべて必須）。
- **FR-4.2** 必須項目が未入力、または形式が不正（郵便番号が 7 桁の数字でない、メールアドレスの形式でない、電話番号が 10〜11 桁の数字でない）なら、項目ごとにエラーを表示して先に進めない。ハイフンは入力されても無視して判定する。
- **FR-4.3** 支払い方法はダミーの選択肢（例: 「クレジットカード（デモ）」「代金引換（デモ）」）だけを表示する。カード番号などの入力欄は設けない。
- **FR-4.4** 注文内容（商品、合計金額、配送先）を確認してから注文を確定できる。
- **FR-4.5** 注文を確定すると、ダミーの注文番号付きの完了画面を表示し、カートを空にする。
  - 判定: 完了画面に注文番号が出て、ヘッダーのカート件数が 0 になる。
- **FR-4.6** カートが空のまま `/checkout` を開いたときはカート画面へ移動する。注文を確定していないのに `/complete` を開いたときは商品一覧へ移動する。

## Non-Functional Requirements

- **NFR-1 ローカルで完結**: `npm install` と `npm run dev` だけで起動できる。外部サービスや API、ネットワーク上の画像に依存しない（商品写真は FR-0.3 のとおり事前にダウンロードしてアプリに同梱する）。
- **NFR-2 セキュリティ**: カード情報の入力欄を持たず、どこにも保存しない。localStorage に保存するのはカートの中身（商品 ID・カラー・サイズ・数量）だけで、配送先などの個人情報は保存しない。API キーや秘密情報は使わない。
- **NFR-3 画面幅**: PC 幅（1280px）とスマートフォン幅（375px）で、横スクロールが出ずに操作できる。
- **NFR-4 品質**: TypeScript の strict モードを使い、ESLint と Prettier を設定する。テストは Minimal 方針とし、Vitest の単体テストを画面の外に出せる処理だけに書く。目安は 3 ファイルで、(1) カテゴリの絞り込み、(2) カート操作（追加・同一行の加算・上限 10・数量変更・削除・合計・壊れた保存値の読み込み）、(3) 配送先の入力チェック。各テストファイルは正常系と、エラー・境界ケース 2 件以上を含む。
- **NFR-5 アクセシビリティの基本**: フォームの各入力にラベルを付け、商品写真には代替テキスト（例: 「ネイビーのパーカー」）を付け、キーボードだけで購入までの流れを操作できる。

## Constraints

- **技術**: React + Vite + TypeScript（Q2）。商品データはアプリに同梱するダミー JSON、カートは localStorage（Q3）。サーバー・DB は使わない。
- **ブランド**: 架空のブランド名「FUKUI BASICS」（仮）を使う（Q4）。ユニクロなど実在ブランドの名称・ロゴ・商品画像は使わない。デザインは白基調・商品グリッドのシンプルなもの。
- **チームの進め方**（`team-practices.md`）: workshop では実デプロイせずローカル実行まで。フォーマッタとリンタを設定する。秘密情報をハードコードしない。カード会員データを自社で保存しない。
- **時間**: ワークショップの残り時間内で、ユーザーストーリー → 画面設計 → コード生成 → ビルドとテストまで進める。

## Assumptions

- UI は日本語、価格は円の税込表示とする（日本向けの自社 EC であるため）。
- 商品は 12 点程度（各カテゴリ 4 点）、各商品に 2〜4 色、サイズ S / M / L / XL を持たせる（一覧と絞り込みを確認するのに十分な量）。
- 在庫は無限とみなし、在庫切れは表示しない（在庫管理は今回の範囲外）。
- 送料・手数料はかからないものとし、合計金額は商品代金の合計とする。
- 一般の利用者がスマートフォンからも使う EC サイトなので、スマートフォン幅での表示（NFR-3）と基本的なアクセシビリティ（NFR-5）を求める。

## Review

**Verdict**: READY

レビュー担当: aidlc-product-lead-agent（Minimal 深度で判定）

良い点: 回答（Q1〜Q4）と `team-practices.md` / `discovered-rules.md` から要件まで、出典が表で追える。主要な要件に合否の判定が付いていて、対象外（ログイン、本物の決済、バックエンド）がはっきりしている。カード情報を持たない方針（FR-4.3、NFR-2）がチームの禁止ルールと一致している。後のステージで違うものを作ってしまうほどの欠落はない。以下はすべて、ユーザーストーリーまたは画面設計で補えば足りる指摘。

1. **[non-blocking] 共通ヘッダーの要件がない。** FR-2.3 と FR-4.5 の合否は「ヘッダーのカート件数」で判定するのに、ヘッダーに何を載せるか（ブランド名を押すと一覧へ戻る、カートへのリンクと件数、全画面に表示）がどこにも書かれていない。共通の要件として 1 行足すとよい。
2. **[non-blocking] 画面とパス（URL）の対応が決まっていない。** FR-2.4 は商品ごとの URL があることを前提にしているが、トップ（`/`）が商品一覧なのか、ルーティングに何を使うか（React Router など）が Constraints に書かれていない。アーキテクチャ設計を省くので、画面の一覧（一覧／詳細／カート／注文手続き／確認／完了）とパスをここで決めておくと、画面設計とコード生成で解釈が分かれない。FR-4.4 の「確認」を別の画面にするか、同じ画面の中の段階にするかも一緒に決める。
3. **[non-blocking] FR-2.3 と FR-3.4 の境目があいまい。** 同じ商品・カラー・サイズがすでに 10 個入っているときに「カートに入れる」を押すとどうなるかが書かれていない。このとき件数は増えないので、FR-2.3 の判定「件数が増える」と食い違う。上限で止めてメッセージを出す、などを 1 行で書く。詳細画面で 1 回押すと 1 個入る、ということも書いておく。
4. **[non-blocking] エラー時の要件が足りない。** (a) localStorage の値が壊れている、または読めないとき（例: 空のカートとして扱う）。(b) カートが空のまま注文手続きや完了画面の URL を直接開いたとき（例: カート画面へ戻す）。この 2 つは Construction のガードレール（外部との境目のエラー処理）にも関わるので、要件にしておくことをすすめる。
5. **[non-blocking] NFR-4 のテストの量があいまいで、時間が足りなくなるおそれがある。** 「要件ごとに 1 本程度」の「要件」が FR-1〜FR-4 の 4 つなのか、FR-1.1〜FR-4.5 の 18 件なのかがわからない。18 件だと、1 ファイルに 3 ケース以上書くので 1 時間では終わらない。テストの対象を、画面の外に出せる処理（カテゴリの絞り込み、カートへの追加・変更・削除と合計、入力チェック）に絞り、ファイル数の目安を書いておくとよい。
6. **[non-blocking] 成功の判定が足りない。** 今は `npm install` と `npm run dev` だけだが、build-and-test ステージで合否を決めるために、`npm run build`、`npm run lint`、`npm test` が通ることも加える。「エラーなく」も、「ブラウザのコンソールに処理されていないエラーが出ない」のように具体的に書く。
7. **[non-blocking] 時間が足りないときに何を削るかが決まっていない。** 残りは約 1 時間なので、必ず作るもの（一覧 → 詳細 → カート → 注文完了の流れ）と、足りなければ削るもの（例: FR-4.4 の確認、FR-4.2 の形式チェック、NFR-3 のスマートフォン幅、NFR-5 のキーボード操作）を分けておくと、後のステージが範囲を守りやすい。
8. **[non-blocking] 細かい食い違い。** Traceability では NFR-3 と NFR-5 を「Assumptions 扱い」としているが、Assumptions の節には書かれていない。FR-2.1 には、一覧（FR-1.1）にある商品画像（プレースホルダ）が入っていない。

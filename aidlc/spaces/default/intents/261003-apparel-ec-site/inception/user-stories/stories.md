# User Stories

> Stage: user-stories（Inception 2.4）· Depth: Minimal
> 入力: `requirements.md`（FR-0〜FR-4、NFR-1〜NFR-5、Priority）、`personas.md`、`user-stories-questions.md`（Q1: B / Q2: A）、`team-practices.md`
> 分け方: 購入の流れの段階ごと（探す → 選ぶ → カートで調整する → 注文する）。優先度は `requirements.md` の Priority に揃えた（Must / Should / Could）。
> ストーリーの優先度と違う受け入れ条件には、条件ごとに〔Should〕〔Could〕を付けた。時間切れで削った条件は、テストの失敗ではなく「未実装」として扱う。
> キッズ商品のサイズ（110 / 120 / 130 / 140）は、`requirements.md` の Assumptions（全商品 S / M / L / XL）よりこのストーリーを優先する。

## 探す

### US-1 商品を一覧で眺める（Must）

P1 として、FUKUI BASICS の商品を写真付きの一覧で眺めたい。なぜなら、どんな服があるかを一目で知りたいからだ。

- 画面: `/` 商品一覧 ／ 要件: FR-0.1、FR-0.3、FR-1.1、FR-1.3
- 受け入れ条件
  - Given アプリを起動した, When `/` を開く, Then 全商品が写真・商品名・税込価格付きのカードで並び、すべての画面に共通のヘッダー（ブランド名とカート件数）が出ている
  - Given 一覧が表示されている, When 商品カードを押す, Then その商品の詳細画面（`/products/:id`）に移動する
  - Given 写真をダウンロードできず、アプリに同梱されなかった商品がある（コード生成時の取得失敗）, When 一覧を開く, Then その商品は商品名とカラーを書いた色付きの枠で表示され、画面は崩れない
  - Given 詳細画面を開いている, When ヘッダーのブランド名を押す, Then `/` に移動する
  - Given 一覧を開いている, When ヘッダーのカートのリンクを押す, Then `/cart` に移動する。リンクの件数はカート内の数量の合計（行数ではない）

### US-2 カテゴリで絞り込む（Should）

P2 として、キッズの商品だけに絞り込みたい。なぜなら、大人用の商品に埋もれずに子ども服を探したいからだ。

- 画面: `/` 商品一覧 ／ 要件: FR-1.2
- 受け入れ条件
  - Given 一覧が表示されている, When 「キッズ」を選ぶ, Then キッズの商品だけが表示される
  - Given 「キッズ」で絞り込んでいる, When 「すべて」を選ぶ, Then 全商品が表示される
  - Given 「メンズ」で絞り込んでいる, When 「ウィメンズ」に切り替える, Then ウィメンズの商品だけが表示され、メンズの商品は残らない

## 選ぶ

### US-3 カラーとサイズを選んでカートに入れる（Must）

P1 として、商品の詳細を見て、カラーとサイズを選んでからカートに入れたい。なぜなら、選び忘れたまま注文するのを防ぎたいからだ。

- 画面: `/products/:id` 商品詳細 ／ 要件: FR-2.1、FR-2.2、FR-2.3、FR-2.5
- 受け入れ条件
  - Given 詳細画面を開いた, When まだ何も選んでいない, Then 写真・商品名・税込価格・説明文・カラーの色見本・サイズが表示され、「カートに入れる」は押せない
  - Given カラーだけを選んだ, When サイズを選ぶ, Then 「カートに入れる」が押せるようになる。選んだ色見本とサイズが強調される〔強調は Should: FR-2.5〕
  - Given カラーとサイズを選んだ, When 「カートに入れる」を 1 回押す, Then 1 個カートに入り、ヘッダーのカート件数が 1 増える
- 補足: キッズ商品のサイズは 110 / 120 / 130 / 140、それ以外は S / M / L / XL（`personas.md` 参照）

### US-4 存在しない商品ページでも迷わない（Should）

P1 として、古いリンクなどで存在しない商品のページを開いても、一覧に戻りたい。なぜなら、行き止まりで買い物をやめたくないからだ。

- 画面: `/products/:id` 商品詳細 ／ 要件: FR-2.4
- 受け入れ条件
  - Given 存在しない商品 ID の URL, When 開く, Then 「商品が見つかりません」と一覧へのリンクが表示される
  - Given その画面, When 一覧へのリンクを押す, Then `/` に移動する

## カートで調整する

### US-5 カートの中身と合計を確認する（Must）

P1 として、カートに入れた商品と合計金額を確認したい。なぜなら、注文する前にいくらになるかを知りたいからだ。

- 画面: `/cart` カート ／ 要件: FR-3.1、FR-3.3、FR-3.5、FR-3.6、FR-3.7
- 受け入れ条件
  - Given カートに 2 行入っている, When `/cart` を開く, Then 各行に商品名・カラー・サイズ・単価・数量・小計が出て、合計金額（税込）が表示される
  - Given カートに商品が入っている, When ブラウザを再読み込みする, Then カートの中身が残っている
  - Given カートが空, When `/cart` を開く, Then 「カートは空です」と表示され、注文手続きへ進むボタンは出ない
  - Given localStorage のカートの値が壊れている, When 画面を開く, Then 画面は表示され、カートは空として扱われる

### US-6 数量を変えたり削除したりする（Should、削除は Must）

P2 として、同じ服をサイズ違いでカートに入れたあと、数量を変えたり不要な行を消したりしたい。なぜなら、きょうだいそれぞれに必要な分だけを買いたいからだ。

- 画面: `/cart` カート、`/products/:id` 商品詳細 ／ 要件: FR-3.2、FR-3.4
- 受け入れ条件
  - Given 同じ商品の 120 と 140 をカートに入れた, When カートを開く, Then 2 つの別の行として表示される
  - Given 同じ商品・カラー・サイズをもう一度カートに入れる, When カートを開く, Then 行は増えず、その行の数量が 1 増えている
  - Given ある行の数量が 1, When 数量を 2 にする, Then 小計が単価の 2 倍になり、合計金額とヘッダーのカート件数も更新される
  - Given カートの数量の選択欄, When 選べる値を見る, Then 1〜10 だけが選べ、0 や 11 は選べない
  - Given ある行の数量が 10, When 詳細画面で同じ商品・カラー・サイズをカートに入れる, Then 追加されず「同じ商品は 10 点までです」と表示され、件数は増えない
  - Given カートに 2 行ある, When 1 行を削除する, Then その行が消え、合計金額が更新される

## 注文する

### US-7 配送先を入力して注文に進む（Must）

P1 として、配送先を入力して支払い方法を選びたい。なぜなら、注文に必要な情報を一度で正しく入れたいからだ。

- 画面: `/checkout` 注文手続き ／ 要件: FR-4.1、FR-4.2、FR-4.3、FR-4.6
- 受け入れ条件
  - Given カートに商品が入っている, When `/checkout` を開く, Then 氏名・郵便番号・住所・電話番号・メールアドレスの入力欄（すべて必須、ラベル付き）と、ダミーの支払い方法の選択肢が表示される。カード番号の入力欄はない
  - Given 氏名が空のまま, When 次へ進もうとする, Then 氏名の欄にエラーが表示され、先に進めない
  - Given 郵便番号に「123-456」（6 桁）と入力した, When 次へ進もうとする, Then 郵便番号の欄に形式エラーが表示される（「123-4567」はハイフンを無視して有効とみなす）〔Could: FR-4.2 の形式チェック〕
  - Given 支払い方法の選択肢, When 画面を開く, Then 「クレジットカード（デモ）」が最初から選ばれている
  - Given すべての必須項目を正しく入力した, When 「次へ」を押す, Then US-8 を作った場合は確認の段階に進み、US-8 を削った場合はそのまま注文が確定して `/complete` に移動する
  - Given カートが空, When `/checkout` を直接開く, Then カート画面に移動する〔Should: FR-4.6〕

### US-8 注文内容を確認してから確定する（Could、時間が足りなければ最初に削る）

P1 として、確定する前に注文内容を見直したい。なぜなら、サイズや住所の間違いで届いてから困りたくないからだ。

- 画面: `/checkout` 注文手続き（確認の段階） ／ 要件: FR-4.4
- 受け入れ条件
  - Given 配送先を正しく入力した, When 次へ進む, Then 商品・合計金額・配送先・支払い方法の一覧が表示され、「注文を確定する」と「入力に戻る」が押せる
  - Given 確認の段階, When 「入力に戻る」を押す, Then 入力済みの内容を保ったまま入力の段階に戻る

### US-9 注文が完了したことを確認する（Must）

P1 として、注文が受け付けられたことを注文番号で確認したい。なぜなら、注文できたかどうか不安なまま終わりたくないからだ。

- 画面: `/complete` 注文完了 ／ 要件: FR-4.5、FR-4.6
- 受け入れ条件
  - Given 確認の段階（US-8 を削った場合は入力の段階）にいる, When 「注文を確定する」（または「次へ」）を押す, Then `/complete` に移動してダミーの注文番号が表示され、ヘッダーのカート件数が 0 になる
  - Given 注文を確定していない, When `/complete` を直接開く, Then 商品一覧に移動する〔Should: FR-4.6〕

| US-3 | US-1 | 一覧から詳細に移動する |
| US-5、US-6 | US-3 | カートに入れる操作が必要 |
| US-7 | US-5 | カートに商品があることが前提 |
| US-8 | US-7 | 入力の後の段階 |
| US-9 | US-7（US-8 を作る場合は US-8） | 注文の確定が必要 |

依存は購入の流れの順序によるもので、各ストーリーはダミーデータと localStorage の初期値を用意すれば単独でもテストできる。

## INVEST Notes

- **Independent**: 依存は流れの順序だけで、テストではカートの初期値を直接用意できる。
- **Negotiable**: Should と Could のストーリーは、時間に応じて削れる（`requirements.md` の Priority と一致）。
- **Valuable**: 各ストーリーはペルソナの目的（P1: 迷わず注文、P2: キッズをサイズ違いでまとめ買い）に結び付いている。
- **Estimable / Small**: 1 ストーリーは画面 1 つ（US-6 のみ 2 画面）に収まる。
- **Testable**: すべての受け入れ条件が Given / When / Then で、操作と結果がはっきりしている。

## Review

**Verdict**: READY

レビュー担当: aidlc-product-lead-agent（Minimal 深度で判定）

良い点: FR-0〜FR-4 のすべてにストーリーが割り当てられていて、Requirements Coverage の表で追える。エラー時の動き（存在しない商品、壊れた保存値、空のカートで `/checkout`、未確定で `/complete`）にも受け入れ条件がある。ペルソナは Q1-B と、分け方は Q2-A と合っている。キッズのサイズ 110〜140 は前提からの変更であることが `personas.md` に明記されている。画面設計とコード生成で違うものを作ってしまうほどの欠落はない。以下はすべて、承認ゲートか画面設計の段階で直せば足りる。

1. **[non-blocking] Must のストーリーに、優先度の低い受け入れ条件が混ざっている。** 「Priority に揃えた」とあるが、US-3（Must）には FR-2.5（Should）の色見本と強調、US-7（Must）には FR-4.2 の形式チェック（時間が足りなければ最初に削る）と FR-4.6（Should）、US-9（Must）には FR-4.6（Should）が、印なしで入っている。US-6 と同じように、受け入れ条件ごとに（Should）（削る候補）などの印を付ける。印がないと、時間切れで削ったときに、削った部分がテストの不合格に見える。
2. **[non-blocking] 注文手続きの「正しく入力して先へ進む」場合の受け入れ条件が、Must のストーリーにない。** US-7 にはエラーの場合しかなく、正常に進む場合は US-8（Could）にしかない。US-8 を削ったとき、入力の段階のボタンの名前と行き先（直接注文を確定して `/complete` へ進むのか）が決まらない。US-7 に「すべて正しく入力した, When 次へ進む, Then 確認の段階へ（US-8 を作らない場合は注文を確定して `/complete` へ）」を足す。あわせて、支払い方法は最初から 1 つ選ばれているのか、選ばないと進めないのかも書く。US-9 の 1 つ目は When が操作になっていない（「完了画面が表示される」）ので、「注文を確定するを押す」にする。
3. **[non-blocking] 共通ヘッダー（FR-0.1）の受け入れ条件が足りない。** 「カート件数」が行の数なのか数量の合計なのかが、ストーリーだけでは分からない（FR-0.1 では数量の合計）。ブランド名を押すと `/` に戻る、カートへのリンクで `/cart` に移動する、の 2 つも確認されていない。「同じ商品・カラー・サイズを 2 回入れると、行は 1 つでヘッダーは 2」「カートで数量を変えるとヘッダーも変わる」のような受け入れ条件を足す。
4. **[non-blocking] 境目のケースが一部抜けている。** (a) カートの数量は 1〜10 の範囲で変えられる（FR-3.2）が、カート画面で 1 より小さく、10 より大きくできないことの確認がない。上限 10 の確認は詳細画面からの追加だけ。(b) US-1 の「写真の取得に失敗した商品がある」が、ダウンロードできずに写真を同梱しなかった商品（FR-0.3）なのか、実行中に画像の読み込みが失敗した場合なのかが分からず、QA がテストの準備をできない。どちらを指すのか（または両方か）を書く。
5. **[non-blocking] キッズのサイズの変更（110〜140）を承認したら、`requirements.md` にも反映する。** 変更自体は明記されていて問題ない。ただ、`requirements.md` の Assumptions には「全商品 S / M / L / XL」が残っている。コード生成のときにダミーデータを Assumptions から作ると、キッズ商品も S〜XL になってしまう。承認したら、Assumptions を直すか、ストーリーを優先すると書いておく。

**Builder response**: 指摘 1〜5 をすべて反映した（条件ごとの優先度ラベル、US-7 の正常に進む条件と支払い方法の初期選択、US-9 の When を操作に修正、ヘッダーの条件を US-1・US-6 に追加、カートの数量範囲、写真の取得失敗を「コード生成時に同梱できなかった場合」と定義、キッズのサイズはストーリーを優先すると冒頭に明記）。
